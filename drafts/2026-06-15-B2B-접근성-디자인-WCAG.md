# B2B 대시보드에 WCAG가 필요한 진짜 이유: "쓸 수 있는 사람"의 폭을 넓히는 접근성 디자인

> "접근성은 장애인을 위한 기능이 아니라, 더 많은 사람이 우리 제품을 쓸 수 있게 만드는 디자인 원칙이다."

## 서론 — 접근성, B2B에선 다르게 다가온다

B2C 서비스의 접근성 논의는 익숙합니다. 음성 인식, 색맹 모드, 자막 기능 — 사용자 다양성을 직접 마주하는 영역이니까요. 그런데 B2B 데이터 분석 서비스 디자이너로서 매일 부딪치는 현실은 조금 다릅니다.

- **고객사 보안 정책**이 키보드만으로 작업하도록 강제하는 경우
- **40대 후반~60대 결정권자**가 작은 폰트에 줌을 200%까지 띄워 쓰는 경우
- **장시간 야간 근무**로 시각 피로가 누적된 운영 담당자가 쓰는 경우

이들 모두 "장애인"으로 분류되진 않지만, **장애 조건과 동일한 사용 맥락**을 갖습니다. WCAG(Web Content Accessibility Guidelines)는 이런 다양한 맥락을 모두 한 자에 담는 표준입니다. 이번 글은 B2B 데이터 분석 서비스에서 WCAG 2.2의 핵심 원칙 4가지를 어떻게 실무에 녹일 수 있는지 정리해 봅니다.

---

## 본문

### 1. 인지 가능(Perceivable) — 색만으로 의미를 전달하지 마라

대시보드에서 가장 흔히 무너지는 원칙입니다. "빨강은 위험, 초록은 정상"이라는 컨벤션은 색맹(인구의 약 8%)에게 정보가 0이 되는 순간이 됩니다.

**B2B 디자인 적용 포인트**
- 상태 표시는 **색 + 아이콘 + 텍스트** 3중 인코딩으로 구성
- 차트 라인은 컬러 외에 **점선/실선/마커 형태**로 추가 구분
- 명도 대비(WCAG AA 기준 **4.5:1 이상**) 검증을 디자인 시스템 토큰 단계에서 자동화

> 💡 실무 팁: Figma 플러그인 "Stark" 또는 "Able"을 디자인 시스템 라이브러리에 묶어두면, 토큰을 새로 추가할 때마다 대비비가 자동 측정됩니다.

### 2. 운용 가능(Operable) — 키보드만으로 모든 기능에 도달할 수 있어야 한다

마우스 호버에 의존한 인터랙션은 키보드 사용자, 터치 사용자, 스크린리더 사용자 모두에게 장벽입니다. B2B에서는 의외로 **금융권 고객사**처럼 마우스 사용 자체가 제한된 환경이 적지 않습니다.

**B2B 디자인 적용 포인트**
- 필터, 정렬, 셀 편집 등 **모든 액션에 키보드 단축키 부여**
- 포커스 인디케이터(focus ring)는 **2px 이상, 대비비 3:1 이상**으로 명확하게
- 호버에만 노출되는 정보(툴팁, 액션 아이콘)는 **포커스 시에도 동일하게 노출**
- 데이터 테이블은 **TAB → 셀 단위 이동**, **Enter → 드릴다운**, **Esc → 닫기** 같은 일관된 패턴 채택

### 3. 이해 가능(Understandable) — 예측 가능성과 일관성

데이터 분석 서비스는 본질적으로 정보 밀도가 높습니다. 그래서 같은 의미의 컨트롤이 화면마다 다르게 동작하면 학습 곡선이 가파르게 올라갑니다.

**B2B 디자인 적용 포인트**
- "저장" / "적용" / "확인" 같은 비슷한 단어를 **하나의 의미로 통일** (디자인 시스템 카피 가이드 정착)
- 에러 메시지는 **무엇이 / 왜 / 어떻게**를 한 줄에 — "필터 조건이 너무 좁아 결과가 0건입니다. 날짜 범위를 7일 → 30일로 넓혀보세요"
- **자동 제출(autosubmit) 금지** — 폼 변경 시 명시적인 사용자 액션을 거치게

### 4. 견고함(Robust) — 보조 기술과 협업 가능한 마크업

스크린리더는 곧 **API**라고 생각하면 디자인 결정이 달라집니다. 우리가 만든 UI가 의미 단위(semantic)를 잘 노출하는지가 핵심입니다.

**B2B 디자인 적용 포인트**
- 차트는 SVG 안에 `<title>`, `<desc>`을 넣어 **요약 텍스트**를 동봉
- 동적으로 갱신되는 알림은 `aria-live="polite"`로 스크린리더에 안내
- 모달은 `role="dialog"` + `aria-labelledby`로 정의해 포커스 트랩을 명시적으로
- 개발자 협업 시 **컴포넌트 단위로 접근성 체크리스트**(키보드 / 스크린리더 / 명도 / 의미)를 PR 템플릿에 포함

---

### B2B 접근성을 가속하는 3가지 운영 원칙

1. **디자인 시스템에 접근성 검증을 빌트인** — 색상 토큰 추가 PR에 대비비 측정 자동화. 새로운 컴포넌트는 키보드/스크린리더 시나리오 테스트를 통과해야만 머지.
2. **접근성을 PM/QA의 공동 책임으로** — 디자이너 혼자 떠안으면 1년 안에 무너집니다. QA 체크리스트에 키보드 탐색 / 스크린리더 1분 청취가 들어가야 지속 가능합니다.
3. **고객사 보안 정책을 접근성 입구로 활용** — 금융권/공공 영역의 키보드 전용 정책, 화면 줌 정책은 곧 접근성 검증의 기회입니다. 정책 대응 과정에서 표준 컴포넌트의 한계가 드러나기 때문입니다.

## 결론 — "쓸 수 있는 사람"의 폭이 곧 제품의 가치다

B2B SaaS에서 접근성은 단순한 컴플라이언스가 아닙니다. 그것은 **장애를 가진 1명의 사용자**, **마우스를 쓸 수 없는 100명의 보안 환경 사용자**, **눈이 피로한 1만 명의 야간 운영자**를 모두 같은 방식으로 돌보는 디자인 원칙입니다.

WCAG 4원칙(인지·운용·이해·견고)은 오래된 표준이지만, 데이터 분석 서비스처럼 정보 밀도가 높은 제품에서 더욱 강력하게 작동합니다. 지금 다루는 대시보드의 빨강·초록 상태 뱃지부터, 차트 호버 툴팁, 그리고 모달의 포커스 트랩까지 — 하나씩 점검해 보면 우리 제품이 닿을 수 있는 사용자의 폭이 얼마나 좁았는지 다시 보일 겁니다.

작은 토큰 하나의 대비비를 4.5:1로 맞추는 일이, 결국 한 명의 사용자가 일을 끝낼 수 있는지 없는지를 결정합니다.
