# 느린 게 아니라 '느리게 느껴지는' 것 — B2B 분석 도구의 체감 성능을 끌어올리는 도허티 임계값 설계법

> UX의 법칙들 스터디 노트에서 출발해, B2B 데이터 분석 서비스 디자이너의 시선으로 다시 정리한 글입니다.

## 들어가며

B2B 데이터 분석 도구를 만들다 보면 한 번쯤 이런 피드백을 받습니다. "조회가 너무 느려요." 그런데 백엔드 로그를 열어보면 쿼리 응답은 1초 안쪽. 분명 빠른데, 사용자는 느리다고 말합니다.

간극의 정체는 **체감 성능(perceived performance)**입니다. 사용자가 경험하는 속도는 서버의 실제 응답 시간이 아니라, 무언가를 요청한 순간부터 의미 있는 반응을 받기까지의 심리적 시간입니다. 이 심리적 시간을 다루는 가장 오래된 UX 법칙이 **도허티 임계값(Doherty Threshold)**입니다.

## 도허티 임계값이란

1982년 IBM의 월터 도허티(Walter J. Doherty)는 컴퓨터의 응답 시간이 **400밀리초(0.4초)** 아래로 떨어지면, 사용자의 생산성이 비약적으로 올라간다는 사실을 밝혀냈습니다. 단순히 기다리는 시간이 줄어서가 아닙니다. 응답이 충분히 빨라지면 사람은 흐름(flow)에 머무릅니다. 시스템과 사용자가 서로를 기다리지 않고, 생각의 속도에 맞춰 대화하듯 작업하게 됩니다.

반대로 응답이 400ms를 넘기기 시작하면 주의가 끊기고, 1초를 넘으면 지금 뭔가 처리 중이라는 인식이, 10초를 넘으면 멈춘 거 아닌가 하는 의심이 생깁니다. 도허티 임계값은 속도의 문제가 아니라 몰입의 문제입니다.

## B2B 분석 도구에서 400ms가 특히 어려운 이유

소비자 앱은 보통 작은 데이터를 빠르게 보여주면 됩니다. 하지만 B2B 분석 도구는 태생적으로 무겁습니다.

- 수백만 행을 집계하는 쿼리
- 여러 차원을 교차하는 피벗·코호트 분석
- 외부 데이터 소스와의 실시간 연동
- 권한·필터 조합에 따라 매번 달라지는 결과

이런 환경에서 모든 요청을 400ms 안에 끝내는 건 비현실적입니다. 그래서 분석 도구의 디자이너는 발상을 바꿔야 합니다. 실제 속도를 400ms로 만드는 게 아니라, 사용자의 체감을 400ms처럼 느끼게 설계하는 쪽으로요.

## 체감 성능을 끌어올리는 6가지 설계 장치

### 1. 즉각적인 피드백으로 수신 신호부터 보낸다

사용자가 조회 버튼을 누른 그 100ms 안에 무언가 반응해야 합니다. 버튼이 눌린 상태로 바뀌고, 로딩 인디케이터가 뜨고, 결과 영역이 불러오는 중 상태로 전환되는 것. 결과가 아직 없어도 요청을 접수했다는 신호만으로 체감 대기 시간은 크게 줄어듭니다. 침묵이 가장 느립니다.

### 2. 스켈레톤 스크린으로 완성 형태를 미리 보여준다

빈 화면에 스피너 하나를 돌리는 것보다, 실제 차트와 표가 들어설 자리에 회색 골격(skeleton)을 먼저 그려주는 편이 훨씬 빠르게 느껴집니다. 사용자의 뇌는 이미 결과의 레이아웃을 인지하기 시작하고, 구조가 보이니 곧 채워지겠다고 예측합니다. 스피너는 얼마나 걸릴지 모른다는 신호이고, 스켈레톤은 이 모양으로 곧 나온다는 신호입니다.

### 3. 점진적 렌더링으로 일부라도 먼저 보여준다

대시보드 전체가 다 준비될 때까지 기다리지 마세요. 가벼운 요약 카드(KPI 숫자)는 0.2초 만에, 무거운 시계열 차트는 1.5초 뒤에 채워지더라도, 사용자는 첫 숫자를 보는 순간 이미 작업을 시작합니다. 무거운 위젯일수록 화면 아래쪽·후순위에 배치해, 첫 화면(above the fold)이 가장 먼저 완성되도록 우선순위를 줍니다.

### 4. 낙관적 업데이트(Optimistic UI)로 결과를 앞당긴다

필터를 토글하거나 항목을 즐겨찾기에 추가하는 등 성공 확률이 높은 동작은, 서버 응답을 기다리지 않고 UI를 먼저 바꿉니다. 실패하면 그때 되돌리면 됩니다. 사용자 입장에선 반응이 0ms처럼 느껴집니다. 단, 분석 결과 자체처럼 정확성이 중요한 데이터에는 신중히 적용해야 합니다.

### 5. 진행률 표시로 끝이 보인다는 안도감을 준다

400ms를 넘길 수밖에 없는 무거운 쿼리라면, 솔직하게 진행 상황을 보여주세요. 막연한 무한 스피너보다 "12개 데이터 소스 중 8개 집계 완료" 같은 구체적 진행률이 체감 시간을 줄입니다. 끝이 보이면 사람은 덜 초조합니다. 진행 바가 멈춘 듯 보일 땐 단계별 메시지로 지금 무엇을 하는 중인지를 함께 전하면 신뢰가 유지됩니다.

### 6. 예측·캐싱으로 기다림 자체를 없앤다

사용자가 자주 보는 기간·필터 조합은 미리 계산해 캐싱해두고, 다음 동작을 예측해 백그라운드에서 선조회(prefetch)합니다. 어제 본 리포트, 이번 주 기본 대시보드처럼 습관적 경로는 거의 즉시 떠야 합니다. 가장 빠른 응답은, 사용자가 요청하기 전에 이미 준비된 응답입니다.

## 빠른 게 항상 옳지는 않다

흥미롭게도 도허티 임계값에는 반대 방향의 함정도 있습니다. 너무 빨라도 신뢰를 잃는 경우입니다. 복잡한 재무 분석이나 신용 평가 결과가 0.1초 만에 튀어나오면, 사용자는 제대로 계산된 건지 의심합니다. 이럴 땐 일부러 의도된 지연(benevolent delay)과 정밀 분석 중 같은 단계 메시지를 넣어, 결과에 무게감을 부여하는 편이 신뢰를 높입니다.

디자이너의 일은 무조건 빠르게 만드는 것이 아니라, 각 작업의 성격에 맞는 적절한 체감 속도를 설계하는 것입니다. 가벼운 탐색은 흐름이 끊기지 않도록 즉각, 무거운 의사결정은 신뢰가 쌓이도록 적당히.

## 마치며

체감 성능을 챙기는 디자이너는 개발자에게 서버를 더 빠르게 해달라고만 요구하지 않습니다. 대신 묻습니다. 사용자가 가장 먼저 봐야 할 한 가지는 무엇인가, 그것만이라도 400ms 안에 띄울 수 있을까.

도허티 임계값은 1982년의 발견이지만, 데이터가 점점 무거워지는 지금의 B2B 분석 도구에 오히려 더 절실합니다. 실제 쿼리 속도를 끌어올리는 엔지니어링 노력과, 체감 속도를 설계하는 디자인 노력은 함께 가야 합니다. 사용자는 밀리초가 아니라 흐름을 기억하니까요.
