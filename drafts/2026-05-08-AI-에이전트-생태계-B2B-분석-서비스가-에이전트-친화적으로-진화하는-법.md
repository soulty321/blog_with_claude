# AI 에이전트 생태계, B2B 분석 서비스가 '에이전트 친화적'으로 진화하는 법

> 사람만 쓰던 대시보드에 이제 에이전트가 노크합니다. 우리는 어떤 문을 열어줘야 할까요?

## 들어가며

"이 데이터, ChatGPT한테 분석시켜서 가져와요." 요즘 이런 요청을 부쩍 자주 듣습니다. 사용자가 직접 필터를 만지작거리는 시간보다, AI 에이전트에게 일을 넘기고 결과만 받는 시간이 빠르게 늘고 있어요.

단순한 도구 교체가 아닙니다. 사용자 자리에 에이전트가 들어선 사건이에요. 우리가 만드는 제품의 정의 자체를 흔드는 변화죠.

---

## 1. 지금 에이전트 생태계는 어디까지 왔나

지난 2년 사이 'AI 에이전트'의 의미가 크게 바뀌었어요. 2023~2024년에는 단일 LLM이 단일 답변을 주는 챗봇이 대부분이었지만, 2025~2026년 현재는 도구를 호출하고 다단계로 추론하며 외부 API와 협업해 작업을 끝까지 완료하는 자율 행위자로 진화했어요.

핵심은 두 가지예요. 첫째, 에이전트가 외부 서비스를 부르는 방식(함수 호출, MCP 같은 표준)이 점점 정립되고 있어요. 우리 제품이 에이전트가 부를 수 있는 형태로 노출돼 있지 않다면, 다음 세대 사용자에게는 보이지 않는 제품이 됩니다.

둘째, 에이전트가 다른 에이전트를 호출하는 멀티 에이전트 협업도 흔해졌어요. 사용자는 오케스트레이터 역할만 하고, 실제 작업은 여러 에이전트가 분업합니다. 우리 서비스는 여러 에이전트가 동시에 접근하는 환경에 놓이게 돼요.

---

## 2. 우리 앞에 놓인 3가지 도전

### ① UI는 사람, API는 에이전트 — 균형 잡기

대시보드는 사람 눈에 최적화돼 있어요. 그래프, 필터, 인사이트 패널. 근데 에이전트는 이런 걸 거의 안 봐요. 에이전트가 원하는 건 구조화된 데이터, 잘 문서화된 엔드포인트, 안정적인 응답 스키마예요. UI를 만들 때 이 화면의 인사이트를 에이전트도 그대로 가져가는지 함께 자문해볼 필요가 있어요.

### ② 신뢰 — 잘못된 분석을 어떻게 검증할까

에이전트는 빠르지만 틀려요. B2B에서 틀린 분석은 곧 잘못된 의사결정으로 이어집니다. 그래서 에이전트가 가져간 데이터의 출처와 신뢰도를 사람이 추적할 수 있는 구조가 필요해요. "AI가 이렇게 말했어요"가 아니라, 어떤 쿼리·기간·필터·원본 지표에서 왔는지를 한 번에 거슬러 올라가는 경로를 만들어야 합니다.

### ③ 권한 — 자율성과 통제 사이

에이전트가 사용자 계정으로 데이터를 가져갈 때, 우리는 허락 범위를 설계해야 해요. 읽기 전용인지, 어떤 워크스페이스까지인지, 권한을 언제든 회수할 수 있는지, 행동 로그가 감사 가능한지. 보안만의 문제가 아니라 UX 문제이기도 해요. 권한을 이해 가능한 범위와 시간으로 부여해야 사용자가 마음 편히 위임합니다.

---

## 3. 에이전트 친화적 설계의 5가지 원칙

### ① 기능을 도구(tool)로 노출하기

UI 안에 잠겨 있는 기능을 잘 정의된 함수로 외부에 공개하세요. 함수 이름·인자·결과 스키마가 곧 에이전트가 보는 인터페이스예요. UX 라이팅 원칙(명확함·일관성)이 그대로 함수 네이밍에 적용됩니다.

### ② 결과는 사람용/에이전트용 두 포맷으로

같은 분석 결과를 사람에겐 시각화된 카드로, 에이전트에겐 마크다운+JSON으로 동시에 제공하세요. 양쪽 다 1급 시민으로요.

### ③ 출처를 끝까지 보존하기

모든 숫자에 "이 숫자는 어디서 왔는가"의 링크가 붙어 있어야 해요. 사람이 검증할 수 있어야 에이전트 분석이 의미를 갖습니다.

### ④ 작은 권한, 짧은 수명

에이전트에게 주는 토큰은 좁은 범위, 짧은 만료 시간으로. UI에서는 "이 에이전트는 OO 프로젝트 데이터를 읽을 수 있고, 24시간 후 자동 만료됩니다" 같이 이해 가능한 문장으로 표현해주세요.

### ⑤ 에이전트의 흔적을 사람이 볼 수 있게

에이전트가 어떤 호출을 했고 어떤 결과를 받았는지, 사람의 활동 로그와 같은 자리에 표시하세요. 에이전트를 보이지 않는 협업자가 아니라 이름 붙은 동료로 다뤄야 신뢰가 생깁니다.

---

## 4. 디자이너의 새로운 일 — 두 사용자를 위한 디자인

이제 우리는 두 종류의 사용자를 위해 디자인해야 해요. 하나는 직관과 맥락, 의사결정의 책임을 가진 사람 사용자이고, 다른 하나는 빠르고 반복적이며 구조화된 입력만 받는 에이전트 사용자예요.

이 둘은 다른 인터페이스를 요구하지만, 같은 진실(데이터)을 봐야 합니다. 하나의 진실에 두 가지 얼굴을 입히되, 두 얼굴이 서로 모순되지 않도록 묶어두는 게 디자이너의 임무가 됐어요. 디자이너도 함수 시그니처를 들여다볼 정도의 기술 감각이 필요하고, 엔지니어는 사용자 신뢰에 대한 감각을 키워야 합니다.

가장 좋은 사고 실험이 하나 있어요.

> "오늘 가입한 신규 사용자가 사람이 아니라 에이전트라고 가정해보자. 첫 5분 동안 에이전트가 무엇을 발견하고, 무엇에 막힐까?"

이 질문에 답하려고 노력하는 만큼, 우리 제품은 다음 세대에도 보이는 제품이 될 거예요.

에이전트는 빠른 사용자입니다. 그래서 느린 신뢰가 더더욱 중요해져요.
