# 긴 대화도 처음처럼 — AI 에이전트의 장기 메모리는 어떻게 설계되는가

## 들어가며: "지난번에 말씀드렸는데요…"의 디자인적 무게

B2B 데이터 분석 서비스를 디자인하다 보면, 사용자가 일주일 전 만든 대시보드를 두고 AI 어시스턴트에게 이렇게 묻는 장면을 자주 보게 됩니다.

> "지난번에 잡은 그 코호트, 이번 달 리텐션은 어때?"

이 한 문장에는 디자이너가 풀어야 할 거대한 숙제가 숨어 있습니다. "지난번", "그 코호트"라는 지시어가 가리키는 대상을 에이전트가 **기억하고 있어야** 자연스러운 대화가 가능합니다. 매번 "어떤 코호트를 말씀하시나요?"라고 되묻는 어시스턴트는 사용자에게 *바보 같다*는 인상을 줍니다.

하지만 모든 것을 기억하는 에이전트는 또 다른 문제를 낳습니다. 잘못된 정보가 영원히 따라오고, 사적인 추론을 다른 워크스페이스로 끌고 들어오고, 토큰 비용이 폭발합니다. 결국 **무엇을 기억하고, 무엇을 잊을지**를 결계처럼 정해두는 일이 AI 에이전트 디자인의 새로운 축이 되었습니다.

이번 글에서는 LLM 기반 에이전트의 **장기 메모리(Long-term Memory)**와 **컨텍스트 관리(Context Management)**가 어떤 구조로 동작하는지, 그리고 B2B 서비스 디자이너가 그 위에 어떤 UX 결정을 얹어야 하는지를 정리합니다.

## 1. 단기 메모리 vs 장기 메모리 — 두 종류의 기억

심리학에서 차용한 개념이지만, AI 에이전트에서는 두 메모리가 서로 다른 저장 매체에 기록됩니다.

**단기 메모리 (Short-term / Working Memory)**
- 현재 대화 세션의 **컨텍스트 윈도우** 안에 머무르는 정보
- 모델이 한 번에 "직접 보는" 토큰들 — 대화 직전 N턴, 시스템 프롬프트, 첨부 문서
- 세션이 끝나거나 토큰 한도를 넘으면 사라짐

**장기 메모리 (Long-term Memory)**
- 별도의 저장소(벡터 DB, 그래프 DB, 키-값 스토어)에 보관되는 정보
- 사용자 프로필, 누적된 선호, 과거 대화 요약, 도메인 지식
- 필요할 때 **검색되어** 단기 메모리(컨텍스트)로 끌어올려짐

디자이너가 가장 자주 마주치는 함정은, 이 두 메모리를 사용자에게 같은 것처럼 보여주려 한다는 점입니다. 사용자는 "AI가 기억하고 있다"고 느끼지만, 실제로는 **방금 검색되어 컨텍스트에 주입된** 정보를 보고 있습니다. 이 차이는 평소엔 보이지 않다가 **검색이 실패할 때** 갑자기 드러납니다.

## 2. 장기 메모리의 네 가지 유형

연구·산업계에서 통용되는 분류를 정리하면 아래와 같습니다. (CoALA, MemGPT, LangGraph Memory 등의 프레임워크가 공통적으로 사용하는 구분입니다.)

**(1) 시맨틱 메모리 (Semantic Memory)**
- **무엇을 아는가**에 대한 사실적 지식
- 예: "사용자의 회사는 SaaS B2B다", "주요 KPI는 MRR과 NRR이다"
- 보통 JSON 스키마나 그래프로 저장

**(2) 에피소딕 메모리 (Episodic Memory)**
- **언제 무엇이 있었는가**에 대한 사건 기록
- 예: "2026-05-12에 사용자가 '이탈 코호트 A' 정의를 수정함"
- 시간순 로그 + 벡터 임베딩으로 검색

**(3) 프로시저럴 메모리 (Procedural Memory)**
- **어떻게 하는가**에 대한 절차·도구 사용법
- 예: "이 사용자가 차트를 만들 때 항상 색상 팔레트 X를 선호함"
- 시스템 프롬프트에 누적되거나 파인튜닝으로 흡수

**(4) 워킹 노트 (Scratchpad)**
- 현재 작업에 한정된 임시 기록
- 예: 멀티스텝 분석 도중 "이 단계까지 봤을 때 의심 가설은 Y"
- 작업 종료 시 폐기되거나 요약되어 다른 메모리로 승격

이 분류는 단순한 학문적 사치가 아닙니다. **저장 위치, 갱신 주기, 사용자 공개 여부**가 모두 다르기 때문에, UX 측면에서도 별도의 화면·동작·동의 절차가 필요합니다.

## 3. 컨텍스트 윈도우의 잔혹한 진실

장기 메모리가 아무리 풍부해도, 모델이 한 번에 처리할 수 있는 토큰은 유한합니다. 대형 모델조차 100만 토큰 안팎에서 멈춥니다. 그리고 그 한도에 가까워질수록 **품질은 비선형적으로 떨어집니다.**

이 현상을 업계에서는 "**Lost in the Middle**"이라고 부릅니다. 컨텍스트 맨 앞과 맨 뒤의 정보는 잘 회상하지만, 중간에 박힌 정보는 자주 누락됩니다. 100k 토큰을 욱여넣었다고 100k 토큰만큼 똑똑해지는 게 아닙니다.

그래서 실무에서는 **세 가지 전략**이 함께 쓰입니다.

**(a) 압축 (Compression)**
대화가 길어지면 과거 턴을 요약본으로 대체합니다. 원본은 별도 로그에 남기되 컨텍스트에는 압축된 버전만 두는 식입니다.

**(b) 검색 (Retrieval)**
모든 것을 컨텍스트에 두지 않고, **이번 질문과 관련된 메모리만** 벡터 검색으로 골라 주입합니다. 일명 RAG-스타일 메모리.

**(c) 분할 (Sharding)**
긴 작업을 여러 에이전트·세션으로 나누고, 각자가 부분 결과를 다시 합치는 방식. 멀티 에이전트 오케스트레이션과도 맞물립니다.

디자이너 관점에서 중요한 건, 이 세 가지가 **사용자에게 어떻게 보이는가**입니다. 압축이 일어났다는 사실을 알려야 할까? 검색이 실패했다고 안내해야 할까? "긴 대화는 자동으로 정리됩니다" 같은 한 줄 문구 하나가 신뢰의 갈림길이 됩니다.

## 4. 디자이너가 통제해야 할 다섯 가지 결정점

다섯 가지 결정점은 UI/카피·정보 구조·권한 모델로 곧장 연결됩니다.

**① 무엇을 기억할 것인가**
모든 발화를 다 저장하면 안 됩니다. "이건 다음에도 써 줘"라는 사용자의 명시적 요청과, "이런 패턴은 자동으로 기억해도 안전해" 같은 시스템적 규칙이 함께 작동해야 합니다.
→ **UX 결정:** 메모리 추가/삭제 버튼, 자동 학습 항목의 카테고리 표시.

**② 얼마나 오래 기억할 것인가**
영속적 메모리 / 세션 메모리 / TTL 기반 메모리. B2B에서는 **고객 계약 종료 시 자동 폐기** 같은 정책이 반드시 들어갑니다.
→ **UX 결정:** 보관 기간 안내, 만료 임박 알림.

**③ 누구와 공유할 것인가**
개인 메모리인가, 팀 전체의 공동 메모리인가? 워크스페이스가 갈리는 순간 메모리는 데이터 격리(isolation) 이슈가 됩니다.
→ **UX 결정:** 메모리 스코프 선택 UI(개인/팀/조직), 잘못된 공유 방지 확인 패턴.

**④ 무엇을 잊을 권리가 있는가**
GDPR·국내 개인정보보호법은 "잊혀질 권리"를 보장합니다. 단순히 화면에서 안 보이게 하는 게 아니라 **벡터 임베딩까지 삭제**되어야 합니다.
→ **UX 결정:** "이 메모리 영구 삭제" 액션 + 삭제 완료 증빙.

**⑤ 메모리가 잘못됐을 때 어떻게 복구하는가**
에이전트가 잘못된 사실을 기억해 두면, 그 위에 쌓이는 모든 추론이 오염됩니다. 사용자가 메모리를 **검사·수정·롤백**할 수 있어야 합니다.
→ **UX 결정:** "AI가 알고 있는 것" 뷰, 항목별 편집/이전 버전 복원.

## 5. B2B 데이터 분석 서비스에 적용해 본 한 컷

가상의 사례입니다. 한 분석가가 매주 월요일마다 같은 대시보드를 보며 "어제 대비 이상치 있는지" 묻습니다.

- **단기 메모리:** 오늘 채팅에서 어떤 대시보드를 열고 있는지
- **에피소딕 메모리:** 지난 4주간 이 사용자가 정의한 "이상치" 기준
- **시맨틱 메모리:** 이 워크스페이스의 KPI 사전, 지표 분모/분자 정의
- **프로시저럴 메모리:** 이 사용자는 슬랙 공유 메시지를 표 형식으로 받는 걸 선호함

이 네 층이 결합되어야 "월요일 아침 1분 안에 인사이트 한 줄"이라는 약속을 지킬 수 있습니다. 만약 시맨틱 메모리(KPI 정의)가 비어 있다면, 에이전트는 매번 "MRR을 어떻게 계산할까요?"라고 묻게 됩니다. 만약 프로시저럴 메모리(포맷 선호)가 없다면, 분석가는 매번 답변을 다시 정리해야 합니다.

디자이너의 역할은 **이 네 층을 사용자가 보지 못해도 신뢰할 수 있게**, 그리고 **필요할 때 보고 만질 수 있게** 만드는 일입니다.

## 마치며: 기억하지 않을 자유까지 디자인하기

장기 메모리는 매력적인 단어입니다. "한 번 알려주면 다음엔 안 알려줘도 돼"는 모든 SaaS의 꿈이니까요. 그러나 진짜 좋은 메모리 디자인은 *얼마나 많이 기억하는가*가 아니라 *얼마나 정확하게, 안전하게, 통제 가능하게 기억하는가*에 달려 있습니다.

기억은 권력입니다. 그리고 모든 권력 옵션에는 **거절할 권리**가 따라붙어야 합니다. 사용자가 "이건 기억하지 마"라고 말할 수 있는 버튼 하나가, 결국 그 서비스의 신뢰도를 결정합니다.

다음 번 AI 기능 기획을 할 때, 자동으로 떠오르는 질문을 한 번 더 떠올려 보세요.

> "지금 이 정보를 **언제까지, 누구와, 어떤 형태로** 기억해야 할까?"

그 질문이야말로 디자이너가 가진 가장 강력한 무기입니다.
