# AI 에이전트가 '진짜로 일하는' 순간 — 계획과 추론의 안쪽

> "1,000개의 키워드를 40초 만에 전략 인사이트로 바꾸는 에이전트가 만들어졌을 때, 가장 어려웠던 건 모델이 아니라 '생각의 흐름'을 설계하는 일이었습니다."

## 들어가며 — 똑똑함이 결과로 이어지지 않는 이유

요즘 AI 에이전트를 다루는 글은 대부분 '도구를 어떻게 잘 호출하는가', '메모리를 어떻게 잘 저장하는가'에 집중합니다. 그런데 막상 B2B 데이터 분석 서비스에 에이전트를 붙여보면, 가장 자주 마주치는 문제는 다른 데 있습니다.

> "지표 5개를 보고 결론을 내려달라고 했는데, 그냥 5개를 나열만 하고 끝났어요."

LLM은 충분히 똑똑합니다. 도구도 잘 호출합니다. 그런데 **결과**가 우리가 기대한 형태로 나오지 않습니다. 이 격차의 정체는 결국 한 가지 — **계획(planning)과 추론(reasoning)**입니다.

오늘은 AI 에이전트 생태계의 가장 안쪽, '에이전트가 무엇을 어떤 순서로 생각하게 만들 것인가'를 다뤄보겠습니다. 특히 B2B 데이터 분석 서비스를 만드는 디자이너·PO 관점에서 무엇을 결정해야 하는지 살펴봅니다.

## 1. 추론(Reasoning)이란 무엇인가 — Chain-of-Thought부터 ReAct까지

### Chain-of-Thought (CoT) — 생각을 글로 쓰게 하는 것

가장 기본은 **사고 사슬(Chain-of-Thought)**입니다. 단순히 "답해라"가 아니라 "단계별로 생각하고 답해라"라고 시키는 것만으로도 결과가 달라집니다.

```
프롬프트: "이 매출 데이터에서 이상치를 찾고, 원인 가설 3개를 제안해."

기존 답: "1월에 매출이 떨어졌습니다. 마케팅 부족이 원인입니다."

CoT 답:
- 우선 평균과 표준편차를 계산해보겠습니다.
- 1월 매출이 평균에서 2.3σ 하락했습니다.
- 가능한 가설은: (1) 시즌성, (2) 신규 채널 이탈, (3) 경쟁사 프로모션.
- 시즌성을 확인하려면 작년 1월과 비교해야 합니다.
```

차이는 **결론의 정확도**가 아니라 **결론에 도달하는 경로의 가시성**입니다. 디자이너 관점에서 이건 결정적입니다 — 사용자가 신뢰할 수 있는 결과는 '맞는 결과'가 아니라 '검증 가능한 결과'이기 때문입니다.

### ReAct — 생각과 행동을 교차시키기

CoT가 진화한 형태가 **ReAct (Reasoning + Acting)**입니다. 생각하고, 도구를 호출하고, 결과를 보고, 다시 생각하는 루프.

```
Thought: 이상치 가설을 검증하려면 작년 같은 기간 데이터가 필요하다.
Action: query_db(table='sales', period='2025-01')
Observation: 작년 1월 매출은 평균 수준이었음. 시즌성 가설 기각.
Thought: 그렇다면 신규 채널 이탈을 확인해야 한다.
Action: query_db(table='channel_sales', period='2026-01', group_by='channel')
Observation: SNS 채널이 -47% 하락.
Thought: 결론을 도출할 수 있다.
```

이게 왜 중요하냐면, 데이터 분석 도메인에서는 **"한 번에 답하기 어려운 질문"**이 대부분이기 때문입니다. 사용자의 질문은 추상적이고, 답에 도달하려면 여러 번 데이터를 들여다봐야 합니다. ReAct는 이 과정을 LLM이 스스로 설계하게 만드는 패턴입니다.

## 2. 계획(Planning) — '먼저 다 짜고 시작하기'

추론이 '한 발 한 발 보면서 가는 것'이라면, **계획(Planning)**은 '먼저 지도를 그리고 출발하는 것'입니다. 둘은 보완 관계입니다.

### Plan-and-Execute 패턴

대표적인 패턴이 **Plan-and-Execute**입니다.

1. **Planner**: 사용자 질문을 받으면 먼저 전체 계획을 단계별로 작성.
2. **Executor**: 각 단계를 순서대로 실행 (도구 호출, 데이터 조회, 분석).
3. **Replanner**: 실행 결과를 보고 필요시 계획을 수정.

이 패턴이 ReAct와 다른 점은 **명시적인 계획서가 존재한다**는 것입니다. 디자이너에게 이건 큰 의미를 가집니다 — 사용자에게 **"AI가 지금 무엇을 하고 있는지"**를 보여줄 수 있기 때문입니다.

> 1,000개의 키워드를 40초 만에 전략 인사이트로 변환하는 작업을 설계할 때, 가장 큰 결정은 모델 선택이 아니라 **"계획을 사용자에게 어떤 형태로 보여줄 것인가"**였습니다.

### 계획의 세 가지 결정 포인트

B2B 데이터 분석 서비스에서 계획을 설계할 때 디자이너가 결정해야 하는 것은 세 가지입니다.

1. **계획의 granularity** — 단계를 얼마나 잘게 쪼갤 것인가? 너무 잘게 쪼개면 사용자가 지치고, 너무 굵게 쪼개면 진행 상황이 안 보입니다.
2. **계획의 mutability** — 중간에 계획을 바꿀 수 있게 할 것인가? 데이터 분석에서는 거의 항상 '예'가 정답입니다. 하지만 UI 복잡도가 올라갑니다.
3. **계획의 visibility** — 계획을 사용자에게 어디까지 보여줄 것인가? 너무 다 보여주면 '읽고 싶지 않은 화면'이 되고, 너무 감추면 '블랙박스'가 됩니다.

## 3. Tree-of-Thoughts — 분기와 백트래킹

CoT가 '직선'이고, ReAct가 '한 발씩 보면서 가기'라면, **Tree-of-Thoughts (ToT)**는 '여러 갈래를 동시에 시도하고 가장 좋은 것을 선택'하는 방식입니다.

```
질문: "이 클러스터링 결과를 어떻게 해석해야 할까?"

가지 A: 행동 기반 클러스터링 → 7개 세그먼트 → 너무 많음. 폐기.
가지 B: 의도 기반 클러스터링 → 3개 세그먼트 → 깔끔. 검증 진행.
가지 C: 시간대 기반 클러스터링 → 흥미롭지만 모집단 편향 우려. 보류.

→ B를 메인으로, C를 보조 가설로 제시.
```

ToT는 비용이 큽니다 (LLM 호출 N배). 하지만 **"답이 하나가 아닌 문제"**에서는 압도적으로 강력합니다. 데이터 분석은 본질적으로 답이 여러 개인 영역이기 때문에 ToT를 부분적으로 차용하는 것이 거의 항상 효과적입니다.

## 4. 그래서 디자이너는 무엇을 해야 하는가

계획과 추론은 엔지니어의 영역처럼 보이지만, 사실 **디자이너가 결정해야 하는 것**이 더 많습니다.

### 결정 1: 사고 과정을 어디까지 노출할 것인가

LLM의 사고 과정을 **숨기는** 옵션과 **펼치는** 옵션을 동시에 제공하세요. ChatGPT의 "Show thinking"이 그렇게 동작합니다. 기본은 숨김, 클릭하면 펼침. 이게 정답에 가깝습니다.

### 결정 2: 실수를 어떻게 보여줄 것인가

ReAct 루프에서 LLM은 자주 "잘못된 가설"을 세웠다가 폐기합니다. 이걸 사용자에게 **"이 가설은 검증 결과 기각되었습니다"**라고 보여주면 신뢰가 올라갑니다. 감추면 "왜 이렇게 오래 걸리지?"가 됩니다.

### 결정 3: 사용자가 계획에 개입할 수 있게 할 것인가

HITL(Human-in-the-loop)과 자율성 사이의 균형입니다. B2B에서는 거의 항상 **개입 가능**이 정답입니다. "이 단계는 건너뛰자", "이 단계를 더 자세히 보고 싶다" 같은 컨트롤이 있을 때 PO·분석가들은 도구로서 신뢰합니다.

### 결정 4: 추론 비용을 사용자에게 어떻게 인지시킬 것인가

CoT, ReAct, ToT는 모두 비용이 듭니다. 응답 시간, API 비용, 그리고 사용자의 인지 부하. **"빠른 답"과 "깊은 답"**을 사용자가 선택할 수 있게 만드는 것이 좋은 패턴입니다. 우리 팀에서는 이걸 "Quick scan"과 "Deep dive" 두 모드로 분리했습니다.

## 5. 핵심 정리 — 똑똑한 에이전트보다 '읽히는 에이전트'

| 영역 | 핵심 결정 |
|------|----------|
| CoT | 사고를 글로 쓰게 할 것인가 (거의 항상 yes) |
| ReAct | 한 발씩 보면서 갈 것인가 (데이터 분석은 yes) |
| Plan-and-Execute | 미리 지도를 그릴 것인가 (긴 작업은 yes) |
| Tree-of-Thoughts | 분기를 시도할 것인가 (답이 여러 개일 때 yes) |
| 사고 노출 | 숨김 + 펼침 옵션 (기본은 숨김) |
| 개입 가능성 | B2B는 거의 항상 yes |

AI 에이전트의 성능은 모델의 크기로 결정되지 않습니다. **"무엇을 어떤 순서로 생각하게 만들 것인가"**, 그리고 **"그 생각을 사용자에게 어떻게 보여줄 것인가"** — 이 두 가지를 설계하는 사람이 결국 제품의 품질을 결정합니다.

그리고 이건, 우리 디자이너의 일입니다.
