# 실패의 순간을 신뢰로 바꾸는 에러 상태 디자인 — B2B 데이터 대시보드에서의 에러 메시지 심화

> 사용자가 우리 제품을 미워하게 되는 순간은 화면이 예뻤을 때가 아니라, 실패했을 때다.

프로덕트 디자인에서 가장 소홀히 다뤄지는 화면은 **에러 상태(error state)** 다. 홈, 리스트, 상세, 폼 — 골든 패스의 화면은 몇 번씩 리뷰하지만, 정작 사용자가 제품을 신뢰하거나 이탈할지를 결정하는 순간은 "예상하지 못한 실패"에서 온다. 오늘은 B2B 데이터 분석 서비스라는 맥락 속에서, 왜 에러 상태 설계가 프로덕트 디자이너의 실력을 가늠하는 잣대가 되는지, 그리고 실무에서 어떻게 접근해야 하는지 정리해 본다.

## 왜 에러 화면이 곧 신뢰의 표면인가

사용자는 우리가 제어할 수 있는 성공 경험보다, **제어할 수 없는 실패 경험**에서 제품을 더 오래 기억한다. 특히 B2B 데이터 분석 서비스처럼 "정확한 숫자"를 다루는 제품은, 한 번의 잘못된 에러 처리가 곧 "이 도구를 믿을 수 없다"는 결론으로 이어진다.

에러 상태는 세 가지 방향에서 신뢰의 표면이 된다.

- **정보 신뢰**: 실패했을 때 무엇이 실패했고 어떤 데이터가 반영되지 않았는지 명확히 알려주는가?
- **자율성 신뢰**: 사용자가 스스로 문제를 해결하거나 회피할 수 있는 경로를 제공하는가?
- **관계 신뢰**: 감정적으로 사용자를 배려하는 어투와 태도가 있는가?

세 가지가 모두 무너진 에러 화면은 "죄송합니다. 오류가 발생했습니다"라는 무책임한 한 줄로 요약된다. 반대로 세 가지가 모두 살아있는 에러 화면은 사용자가 "이 팀은 실패까지 미리 생각했구나"라고 느끼게 한다.

## 에러의 4가지 분류: 원인이 다르면 UI도 달라야 한다

에러를 하나의 화면으로 묶어 처리하는 것은 초심자의 실수다. 원인에 따라 사용자가 취할 액션이 완전히 달라지기 때문이다. 필자는 데이터 분석 서비스 실무에서 아래 4분류를 기준선으로 삼는다.

### 1. 시스템 오류 (System Error)
서버 500, 타임아웃, 네트워크 단절 등 우리 인프라나 외부 연결의 실패. 사용자가 원인이 아니다.

- **원칙**: 사용자에게 책임을 전가하지 말 것. "다시 시도" 버튼과 "잠시 후 다시 확인해 주세요"라는 메시지, 그리고 상태 페이지 링크가 세트가 되어야 한다.
- **B2B 팁**: 실패한 시각(timestamp)과 요청 ID를 노출해 두면 CS에서 재현이 폭발적으로 빨라진다.

### 2. 사용자 입력 오류 (Validation Error)
필수 값 누락, 형식 오류, 범위 초과 등. 사용자가 원인이지만, 대부분 우리가 설계로 예방할 수 있었던 실패다.

- **원칙**: 오류를 **입력 지점 옆에서** 실시간으로 알려주기. 폼 전체를 제출한 뒤 화면 상단에 몰아서 보여주는 방식은 인지 부하만 키운다.
- **글쓰기 팁**: 부정문("올바르지 않은 형식입니다")이 아니라 **긍정 지시문**("YYYY-MM-DD 형식으로 입력해 주세요")으로.

### 3. 권한 오류 (Permission Error)
접근 권한이 없거나, 만료된 세션, 요금제 초과 등.

- **원칙**: **왜 안 되는지 + 다음 액션**을 한 문장으로. "이 기능은 Pro 플랜에서 사용 가능합니다. 요금제를 업그레이드하시겠습니까?"처럼 다음 스텝의 문을 열어 두어야 한다.
- **함정**: "권한이 없습니다" 한 줄만 띄우면 사용자는 관리자에게 문의하러 창 밖으로 나가는 데 3분을 쓴다. 문의처 링크·관리자 이름·요금제 정보 중 최소 하나는 함께 노출한다.

### 4. 데이터 오류 (Data Anomaly)
데이터 자체가 없거나, 값이 이상하거나, 계산 결과가 신뢰 구간을 벗어난 경우. B2B 데이터 분석 서비스에서 가장 다루기 까다로운 종류다.

- **원칙**: "데이터가 없습니다"와 "데이터를 가져오지 못했습니다"를 절대 같은 화면으로 처리하지 말 것. 전자는 정보 결핍, 후자는 신뢰 결핍이다.
- **실무 예시**: 대시보드의 특정 그래프가 0을 그릴 때, "값이 0인 것"인지 "값이 없는 것"인지 "가져오지 못한 것"인지 세 가지를 시각적으로 구분해야 사용자가 잘못된 판단을 하지 않는다.

## 에러 메시지 카피 프레임워크: "무엇이 · 왜 · 어떻게"

에러 메시지를 쓸 때 필자는 항상 세 문장으로 나눠서 검토한다.

1. **무엇이 실패했는가 (What)** — 사용자가 방금 시도한 액션에 대한 사실. "리포트 생성이 중단되었습니다."
2. **왜 실패했는가 (Why)** — 사용자가 이해 가능한 수준의 원인. 스택 트레이스나 에러 코드가 아니라, 인간의 언어로. "데이터 소스와의 연결이 30초 이상 응답하지 않았습니다."
3. **어떻게 해결하는가 (How)** — 사용자가 지금 취할 수 있는 액션. "잠시 후 다시 시도하시거나, 연결 설정을 확인해 주세요."

세 문장 중 하나라도 빠지면 사용자는 다음에 무엇을 해야 할지 알 수 없다. 특히 세 번째 "어떻게"가 빠진 에러는 사용자를 무력하게 만든다. 무력함은 이탈의 다른 이름이다.

## 침묵도 에러다: 서서히 무너지는 실패(Graceful Degradation)

가장 위험한 에러는 실패한 티조차 나지 않는 에러다. 데이터 대시보드에서 한 위젯의 API가 실패했는데 UI가 "0"을 정직하게 그려버리면, 사용자는 그 0을 진짜 지표로 믿는다. 이 순간 우리는 사용자에게 잘못된 의사결정을 강요한 셈이 된다.

- **원칙 1**: 실패한 위젯은 실패했다는 사실을 **명시적으로 시각화**한다. 회색 처리, 사선 패턴, "데이터를 불러오지 못했습니다" 뱃지 등.
- **원칙 2**: 다른 위젯까지 함께 죽지 않도록 **부분 실패(partial failure)** 처리 로직을 미리 정의한다. 한 위젯의 에러가 대시보드 전체를 무너뜨리면 안 된다.
- **원칙 3**: 실패 위젯에 "재시도" 액션을 위젯 단위로 제공한다. 페이지 전체를 새로고침하게 하지 말 것.

## B2B 데이터 분석 서비스에 특화된 에러 디자인 체크리스트

일반적인 SaaS와 달리 데이터 분석 서비스의 에러는 아래 세 축을 추가로 점검해야 한다.

- **데이터 신선도**: "이 데이터는 마지막으로 X분 전에 갱신되었습니다"를 항상 노출. 실패 시 "마지막 성공 시각"을 함께 보여준다.
- **집계 범위 명시**: 필터나 기간 범위 때문에 결과가 0인 경우, "선택한 조건에 해당하는 데이터가 없습니다. 조건을 완화해 보시겠어요?"라는 안내 + 필터 리셋 버튼을 제공한다.
- **재현 가능성**: 에러 순간을 캡처해 CS에 공유할 수 있도록 "이슈 보고" 버튼에 요청 ID·타임스탬프·필터 값이 자동으로 포함되도록 설계한다.

## 결론: 에러 화면은 사용자와 팀의 성숙도를 동시에 드러낸다

에러 상태 디자인은 단순한 예외 처리 UI가 아니다. **우리 팀이 사용자의 불안과 신뢰를 어떻게 다루는가**에 대한 태도의 표현이다. 에러 화면이 잘 설계된 제품은 다음과 같은 조직 문화를 뒤에 두고 있다.

- QA·CS·엔지니어링·디자인이 실패 시나리오를 함께 정의한다.
- 로그와 사용자 언어 사이에 번역 레이어를 두는 사람이 있다.
- 실패한 사용자에게 다음 액션을 제안하는 것이 디자이너의 책임임을 팀 전체가 인정한다.

성공 경험이 사용자를 데려온다면, 실패 경험은 사용자를 붙잡는다. 오늘 리뷰 중인 대시보드나 리포트 화면에서 "성공 케이스만 그려져 있는 시안"이 있다면, 지금 바로 옆에 실패 케이스를 나란히 그려 보자. 프로덕트 디자이너의 성장은 자주 그 자리에서 일어난다.
