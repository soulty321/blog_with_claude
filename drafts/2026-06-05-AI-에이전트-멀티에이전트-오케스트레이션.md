# 혼자 일하는 AI는 한계가 있다 — B2B 데이터 분석 서비스에 멀티 에이전트 오케스트레이션이 필요한 이유

## 들어가며 — '똑똑한 한 명'과 '협업하는 셋'

B2B 데이터 분석 서비스를 만들다 보면, 사용자가 묻는 질문이 점점 더 복잡해진다는 것을 느낀다. "지난 분기 우리 카테고리에서 가장 많이 검색된 키워드 상위 10개를 뽑아주고, 그 중에서 경쟁사가 아직 다루지 않은 주제를 알려달라"는 한 줄짜리 질문 뒤에는 사실 검색, 필터링, 비교, 우선순위 정렬이라는 네 가지 작업이 숨어 있다.

처음에는 이 모든 것을 단일 LLM에게 맡겼다. 프롬프트에 도구 사용법, 데이터 소스 위치, 분석 방법, 출력 형식을 한꺼번에 욱여넣었다. 결과는 어떻게 됐을까? 컨텍스트 윈도우는 매번 가득 차고, 답변은 길어졌지만 정확도는 떨어졌다. 하나의 두뇌가 너무 많은 일을 하느라 어느 것도 깊게 하지 못하는 상태였다.

이 문제를 풀기 위해 떠오르고 있는 패턴이 멀티 에이전트 오케스트레이션(Multi-Agent Orchestration)이다. 이번 글에서는 B2B 데이터 분석 서비스를 디자인하는 관점에서 멀티 에이전트가 왜 필요한지, 어떤 패턴이 있는지, 그리고 UX 설계자가 고려해야 할 지점은 무엇인지 정리해본다.

## 본문

### 1. 왜 '오케스트레이션'이라는 단어를 쓸까

오케스트라를 떠올려보자. 바이올린, 첼로, 호른, 팀파니가 각자의 파트를 가지고 있고, 지휘자가 전체를 조율한다. 모든 악기가 같은 멜로디를 동시에 연주하면 그건 오케스트라가 아니다. 각자의 역할이 다르되, 하나의 곡을 향해 정렬되어 있을 때 비로소 오케스트라가 된다.

멀티 에이전트도 마찬가지다. Planner Agent는 사용자 질문을 하위 작업으로 쪼개고, Retriever Agent는 데이터베이스나 외부 소스에서 정보를 가져온다. Analyzer Agent는 수치를 비교하고 패턴을 찾아내며, Synthesizer Agent는 결과를 사람이 읽을 수 있는 보고서로 정리한다. 이들 위에서 Orchestrator가 순서와 맥락, 결과 검증을 분배한다.

각 에이전트는 자신의 도구와 프롬프트, 컨텍스트만 알면 된다. 분업이 명확하면 각자는 깊어진다.

### 2. 단일 에이전트의 한계 — 컨텍스트 오염

단일 에이전트 구조에서 자주 만나는 문제는 세 가지다.

첫째, 컨텍스트 오염(Context Pollution). 데이터 검색 단계의 거대한 JSON을 최종 요약 단계에서도 계속 메모리에 들고 있어야 한다. 토큰 비용은 늘어나고, 모델은 정작 중요한 마지막 지시사항을 흐릿하게 본다. 사람도 그렇다. 회의에서 첫 1시간 동안의 잡담을 기억하면서 결론을 내라고 하면 누구든 흐릿해진다.

둘째, 도구 폭주(Tool Sprawl). 도구를 10개 이상 묶어두면 LLM은 지금 이 상황에서 어떤 도구가 적절한지 고르는 데 인지 자원을 너무 많이 쓴다. 사용자 질문에 답하기도 전에 어떤 도구 메뉴를 켤지 결정하느라 지치는 셈이다.

셋째, 실패의 단일 지점(Single Point of Failure). 한 에이전트가 한 번 잘못된 결론을 내면 그 위에 쌓이는 모든 후속 작업이 오염된다. 검증 단계가 분리되어 있지 않기 때문이다.

### 3. 멀티 에이전트의 세 가지 대표 패턴

**Pattern A. Sequential Pipeline (순차형)**

Planner → Retriever → Analyzer → Synthesizer가 컨베이어 벨트처럼 연결된다. 입력과 출력이 명확하게 정의된 도메인(예: 일간 리포트 자동 생성)에 적합하다. 디버깅이 쉽지만 분기 처리에는 약하다.

**Pattern B. Hub-and-Spoke (허브형)**

중앙의 Orchestrator가 모든 의사결정을 가지고 있고, 각 전문 에이전트는 도구처럼 호출된다. 유연성이 높고, 사용자 의도가 도중에 바뀌어도 대응하기 좋다. B2B 분석 서비스의 대화형 인터페이스에 자주 등장한다.

**Pattern C. Peer Collaboration (수평 협업)**

에이전트들이 서로의 결과를 보고 토론하듯 반복(loop)한다. 정답이 하나가 아닌 창의적 작업(예: 카피라이팅, 디자인 시스템 토큰 명명)에 강하다. 다만 비용이 가장 비싸다.

B2B 데이터 분석 서비스라면 보통 A와 B의 하이브리드가 현실적이다. 정형화된 일일 리포트는 Sequential로, 사용자가 즉석에서 던지는 자유 질문은 Hub-and-Spoke로 처리한다.

### 4. 디자이너가 멀티 에이전트 UI에서 신경 써야 할 것

엔지니어가 아키텍처를 짤 때 디자이너는 무엇을 봐야 할까?

첫째, 진행 상태의 가시화다. 오케스트레이터가 4개의 에이전트를 동시에 호출하면, 사용자는 "검색하는 중", "분석하는 중", "정리하는 중"이 동시에 표시되는 화면을 본다. 모든 에이전트의 상태를 같은 비중으로 보여주면 사용자는 어디를 봐야 할지 모른다. 사용자가 가장 궁금해할 한 가지 진행 상황을 메인으로, 나머지는 보조 인디케이터로 처리하는 위계가 필요하다.

둘째, 중간 산출물의 노출 정도다. Planner가 "이 질문을 3단계로 쪼갰습니다"를 보여주면 사용자는 안심한다. 그러나 Retriever가 가져온 원본 JSON을 그대로 노출하면 압도된다. 결과의 요약을 먼저 보여주고, 펼치기 옵션을 두는 것이 정석이다. Anthropic의 Claude Code 같은 인터페이스가 좋은 사례다 — 도구 호출은 카드로 접고, 사용자가 의심할 때만 펼친다.

셋째, 실패의 정직한 표현이다. 에이전트 중 하나가 실패했을 때, 그 사실을 숨기고 "분석이 완료되었습니다"라고 보고하는 것은 단기적으로 깔끔해 보이지만 신뢰를 망가뜨린다. "Retriever 단계에서 일부 데이터를 가져오지 못했습니다. 가져온 80% 데이터로 분석한 결과는 다음과 같습니다"라고 정직하게 말하는 UI가 장기적으로 이긴다. 분석가는 거짓된 100%보다 정직한 80%를 신뢰한다.

넷째, 사용자 개입 지점(Human-in-the-Loop)의 설계다. 모든 에이전트가 자동으로 끝까지 달리지 않아도 된다. Planner가 작업을 쪼갠 직후, "이 계획대로 진행할까요?" 한 번을 물어보는 것만으로도 사용자는 통제감을 가진다. B2B 사용자, 특히 데이터를 다루는 사람일수록 '내가 들여다보고 승인할 수 있다'는 감각을 중시한다.

### 5. 작은 시작 — 실무에 도입하는 단계

처음부터 5개의 에이전트를 만들 필요는 없다. 점진적으로 도입하는 편이 낫다.

단일 에이전트에 명확한 도구 카탈로그(5개 이하)를 붙이는 것부터 시작한다. 그 다음, 컨텍스트가 자주 오염되는 단계 — 보통 데이터 검색 직후 — 를 분리해 별도 에이전트로 추출한다. 사용자 의도가 자주 분기되는 지점에 Orchestrator를 도입하고, 검증이 필요한 산출물에 Reviewer Agent를 추가한다.

각 단계마다 사용자에게 어떤 가시성을 줄지 함께 디자인해야 한다. 백엔드 아키텍처가 멀티 에이전트로 진화했는데 UI는 여전히 '검색 중...' 한 줄이라면, 사용자는 그 진화의 가치를 체감하지 못한다.

## 결론 — 분업이 만드는 깊이

B2B 데이터 분석 서비스의 진짜 가치는 "빠른 답"이 아니라 "신뢰할 수 있는 답"에서 나온다. 그리고 신뢰할 수 있는 답은 각자가 자기 영역에서 충분히 깊어진 분업에서 나온다.

멀티 에이전트 오케스트레이션은 단순히 LLM을 여러 개 띄우는 기술적 트릭이 아니다. 어떻게 일을 쪼개고, 누구에게 어떤 권한을 주고, 사용자에게 어디까지 보여줄 것인가 — 조직 설계의 디지털 버전이다. 그리고 그 조직을 사용자에게 어떻게 드러낼지가 바로 우리, 디자이너의 몫이다.

오케스트라의 청중은 무대 뒤의 리허설 시간을 모른다. 그러나 정교한 협업이 만들어내는 화음의 깊이는 분명히 듣는다. 우리가 디자인할 멀티 에이전트의 UX도 그래야 한다. 복잡함은 뒤에 숨기고, 신뢰는 앞에 드러내는 것.
