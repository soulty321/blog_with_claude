# 관대한 입력, 엄격한 출력 — 포스텔의 법칙이 B2B SaaS UX를 살리는 이유

> "보내는 것은 보수적으로, 받는 것은 관대하게."
> — Jon Postel, RFC 760 (1980)

## 서론 — 인터넷을 살린 한 줄의 원칙이 UX에도 통한다

40년 전, 인터넷 프로토콜의 아버지 존 포스텔은 TCP 명세서에 한 줄을 적어 넣었습니다. "보내는 것은 엄격하게, 받는 것은 관대하게." 이 짧은 원칙은 서로 다른 기기·OS·네트워크가 무난히 통신할 수 있게 한 비밀이었습니다.

그런데 이 원칙은 기계 사이의 약속을 넘어 **사람과 시스템 사이의 약속**으로 확장됩니다. UX 디자이너 제레미 키스는 이를 "사용자가 입력하는 데이터는 가능한 모든 방식을 관대하게 받아들이고, 시스템이 출력하는 데이터는 일관되고 엄격하게 다듬어야 한다"고 재해석했죠.

특히 데이터 입력이 잦은 **B2B SaaS** 환경에서 이 원칙은 단순한 디테일이 아닌 **전환율과 유지율을 결정짓는 설계 철학**입니다. 오늘은 포스텔의 법칙이 어떻게 일하는 사람들의 마찰을 줄이는지, 그리고 어떤 디자인 패턴으로 구현되는지 살펴보겠습니다.

---

## 본문

### 1. 사용자는 "정해진 형식"을 기억하지 않는다

전화번호 한 칸을 떠올려 봅시다. 사용자는 `010-1234-5678`로 칠 수도, `01012345678`로 칠 수도, `+82 10 1234 5678`로 칠 수도 있습니다. 어떤 형식이 "맞는" 형식일까요?

답은 **모두 맞다**입니다. 사용자가 머릿속에 가진 형식은 본인의 맥락(주소록 저장 방식, 출신 국가, 단축키 습관)에 묶여 있습니다. 그런데 많은 SaaS 폼이 이 다양성을 "잘못된 형식입니다"라는 빨간 에러로 거절합니다.

> 사용자는 형식을 외우지 않습니다. 의도를 입력할 뿐입니다.

포스텔의 법칙이 알려주는 것: **다양한 입력을 모두 받아들이되, 내부적으로는 표준 포맷(예: E.164 국제 표준)으로 통일**하라. 사용자가 어떻게 치든 데이터베이스에는 일관된 `+821012345678`만 저장됩니다.

### 2. "관대한 입력"의 5가지 구현 패턴

데이터 입력 UX에서 포스텔의 법칙을 적용하는 구체적 패턴은 다음과 같습니다:

**① 공백·하이픈·괄호 자동 무시**
사용자가 친 `010 1234-5678`, `(010)1234.5678`을 모두 동일하게 처리합니다. JavaScript 한 줄(`value.replace(/\D/g, '')`)이면 끝나는 일을 "올바른 형식으로 입력해 주세요"로 거절하는 폼은, 사용자가 아니라 개발자의 편의를 우선한 설계입니다.

**② 대소문자 비구분**
이메일·아이디·세금번호 등 본질적으로 대소문자 의미가 없는 필드는 입력 시 자동 변환해 저장합니다. `John@gmail.com`과 `john@gmail.com`을 다른 계정으로 만드는 SaaS는 가입 후 1주일 안에 "계정이 없습니다" 문의를 받게 됩니다.

**③ 단위 자동 추론**
무게 `1.5kg`과 `1500g`, 길이 `1.2m`와 `120cm`를 모두 받습니다. 단위를 명시하지 않은 입력은 필드 옆에 표시된 기본 단위로 해석합니다. 풀필먼트·물류 SaaS에서 이 한 가지만 적용해도 입력 오류율이 절반으로 줄어든 사례가 있습니다.

**④ 날짜·시간 자연어 파싱**
`내일 오후 3시`, `2026-05-29 15:00`, `5/29 15:00`을 모두 같은 시점으로 해석합니다. 캘린더 위젯을 강제로 띄우기 전에, 사용자가 친 그대로의 텍스트를 한 번 해석해 보세요. Linear, Notion, Things 같은 도구가 사랑받는 이유 중 하나입니다.

**⑤ 부분 입력 자동 보완**
URL을 `wanted.co.kr`처럼 프로토콜 없이 적어도 `https://wanted.co.kr`로 자동 보완합니다. 도메인 이름이 명백한데 "유효한 URL이 아닙니다"라고 거절하는 폼은 디자이너가 사용자의 의도를 한 번 더 의심해 봐야 합니다.

### 3. 그러면 "엄격한 출력"은 어떻게?

관대함이 무한정이면 데이터는 진흙탕이 됩니다. 한쪽 사용자는 `+82-10-1234-5678`로, 다른 쪽은 `010 1234 5678`로 저장되면, **검색·필터·외부 연동에서 깨지기 시작**합니다.

엄격한 출력의 핵심 규칙은 세 가지입니다.

1. **단일 표준 포맷으로 정규화한 뒤 저장**: 전화는 E.164, 통화는 ISO 4217 코드와 함께, 날짜는 ISO 8601(UTC).
2. **표시는 사용자 컨텍스트에 맞게 재포맷**: 저장은 `+821012345678`이지만 한국 사용자에게는 `010-1234-5678`, 일본 사용자에게는 `010-1234-5678`로 표시.
3. **외부 API·내보내기·연동에서는 표준 포맷 그대로**: CSV 내보내기, 웹훅, Zapier 연동에서 사용자 표시 포맷이 아닌 표준 포맷을 사용해 통합 깨짐을 방지.

### 4. 포스텔의 법칙과 마찰의 경제학

데이터 입력 폼에서 사용자가 마주치는 마찰은 **두 가지**입니다.

- **인지적 마찰**: "이 필드의 정확한 형식이 뭐였더라?"
- **운동적 마찰**: 하이픈을 빼고 다시 치기, 공백을 지우기

이 두 마찰을 모두 사용자에게 떠넘기면 폼 완료율은 떨어집니다. 그런데 디자이너 한 명이 정규화 로직 30줄을 추가하면, 수천 명의 사용자가 그 마찰에서 해방됩니다. 이게 포스텔의 법칙의 경제학입니다. **소수 디자이너·개발자의 한 번의 노력이 대다수 사용자의 반복적 고통을 제거**합니다.

데이터 분석 SaaS의 경우 한 단계 더 나아갑니다. 사용자가 업로드하는 CSV의 헤더 이름이 `email`, `Email`, `이메일`, `E-mail`로 다를 수 있죠. 똑똑한 SaaS는 이를 모두 같은 컬럼으로 인식하고, **사용자에게 "확인해 주세요"라고 묻습니다**. 잘못된 헤더를 거절하지 않고, 추론하고, 검증 권한을 사용자에게 돌려주는 방식입니다.

### 5. 관대함의 함정 — 어디서 멈춰야 하는가

포스텔의 법칙도 만능은 아닙니다. 보안과 무결성이 걸린 영역에서는 "관대한 입력"이 곧 취약점이 됩니다.

- **비밀번호 입력**: 앞뒤 공백 자동 트림은 OK, 그러나 대소문자 비구분은 NO.
- **결제 금액**: 단위 추론은 위험. `1000` 입력이 ₩1,000인지 ₩100,000(천원 단위)인지 사용자 확인 단계 필수.
- **이메일 도메인**: `gmail.con` 같은 오타 자동 교정은 친절하지만, **사용자에게 한 번 확인**하는 것이 안전.

핵심은 **마찰 ≠ 악**이라는 것입니다. 의도된 마찰은 사용자를 위한 안전장치입니다. 포스텔의 법칙은 "불필요한 마찰만 줄이라"는 원칙이지, "모든 마찰을 없애라"가 아닙니다.

## 결론 — 좋은 시스템은 사용자보다 똑똑하다

포스텔의 법칙이 40년이 지나도 살아 있는 이유는 단순합니다. **시스템이 사용자보다 일하기에 적합**하기 때문입니다.

- 사람은 형식을 기억하지 못합니다. → 시스템이 형식을 추론합니다.
- 사람은 단위를 까먹습니다. → 시스템이 컨텍스트로 채웁니다.
- 사람은 일관성을 유지하지 못합니다. → 시스템이 표준으로 통일합니다.

그리고 그 결과는 사용자에게 보이지 않습니다. 좋은 정규화 로직은 사용자가 알아채지 못해야 하니까요. 알아채는 순간은 단 하나, **에러가 사라졌을 때**입니다.

여러분이 다음에 폼을 설계할 때, 한 번 자신에게 물어보세요. "이 에러 메시지는 정말 사용자가 봐야 하는가, 아니면 내가 5분 더 코드를 짜면 사라지는가?"

대답이 후자라면, 포스텔이 인터넷에 한 것을 여러분도 SaaS에 할 수 있습니다.
