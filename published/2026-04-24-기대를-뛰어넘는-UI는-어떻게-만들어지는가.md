"기대를 뛰어넘는 UI"라고 하면 어떤 게 떠오르세요?

화려한 애니메이션? 깜짝 놀랄 만한 인터랙션?

근데 TeamLab의 답은 좀 달랐어요. **사용자가 진짜 원하는 걸 본질적으로 채워주는 것**, 그게 기대를 뛰어넘는 UI라고 하더라고요.

---

## 좋은 UI를 다시 생각해 보기

이토 씨가 던진 질문은 단순했어요. "본질적으로 응답한다는 게 뭘까?"

그가 정리한 흐름은 이렇습니다.

```
사용자 욕구 → 서비스 → 프로덕트 → UI
```

그런데 이 흐름이 한 방향만은 아니에요. UI에서 욕구가 채워지면, 또 새로운 욕구가 생기죠. 그래서 그 안에서 **공통으로 흐르는 축**을 찾는 게 출발점이라고 합니다.

말이 좀 추상적인데, 사례로 보면 이해가 빨라요.

---

## 사례 1: 일본우편 앱 — 서비스가 아니라 '내 짐'이 중심

기존 일본우편 앱은 60여 개 서비스가 쭉 나열돼 있었어요. 사용자는 하나씩 눌러보면서 어떤 게 자기 상황에 맞는지 비교해야 했죠.

팀이 욕구를 따라가 봤더니, 흐름이 이렇게 나왔습니다.

- 택배를 보내고 싶다
- 내 짐 조건(크기, 가격)에 맞는 서비스를 고르고 싶다
- 보낸 다음엔 어디 있는지 추적하고 싶다

공통 키워드가 보이시나요? **'내 손에 있는 화물'** 이었어요.

그래서 리디자인 후엔 짐의 크기나 무게를 먼저 입력하면, 적합한 서비스가 자동으로 추려져 나옵니다. 내비게이션의 축이 '서비스'에서 '내 짐'으로 바뀐 거예요.

![그래픽 사용자 인터페이스 애플리케이션 화면](https://unsplash.com/photos/graphical-user-interface-application-Uln4sEaUwGE/download)

### 실무자의 시선 — '욕구 연쇄'를 따라가면 진짜 문제가 보인다

이 사례를 보면서 제 경험이 바로 떠올랐어요. 마이키워드 프로젝트에서도 똑같은 일이 있었거든요.

고객이 처음에 말한 요구사항은 **"엑셀 다운로드를 더 편하게 해달라"**였어요. 하지만 인터뷰를 깊이 파고들자, 진짜 욕구는 **"지난달 데이터와 비교하고 싶다"**였습니다. 엑셀은 비교 기능이 서비스에 없어서 발생한 우회 행동이었던 거죠.

욕구 연쇄로 풀면 이런 체인이에요:

```
다운로드 편의 → 데이터 비교 → 시장 변화 파악 → 더 나은 의사결정
```

일본우편이 '서비스 나열'에서 '내 짐 중심'으로 축을 바꿨듯이, 저는 '엑셀 다운로드 개선'에서 '서비스 내 자동 비교 기능 구축'으로 방향을 바꿨어요. 결과는 처리 시간 99% 단축(3일→1분)과 엑셀 작업 완전 제거였습니다.

---

## 사례 2: 나리타 공항 — 진짜 원하는 건 '시간 관리'였다

처음에 팀은 "사용자는 시설 위치를 알고 싶어한다"고 생각했어요. 그래서 위치 정보를 중심에 두려고 했죠.

근데 한 번 더 들어가 보니 다른 게 나왔습니다.

> "왜 그 장소를 알고 싶을까? → 탑승 시간에 맞춰 이동해야 하니까."

진짜 욕구는 위치가 아니라 **시간 관리**였던 거예요.

그래서 앱에는 이런 게 들어갔습니다.
- 체크인 카운터·게이트로 바로 이동하는 링크
- 보안 검색대 실시간 혼잡도
- 목적지까지 이동 시간 자동 계산

단순 지도가 아니라, "지금 출발하면 몇 분 후 게이트 도착"을 사용자가 직접 판단할 수 있는 도구가 된 거죠.

## 데이터와 사양은 UI의 '재료'

이토 씨가 강조한 또 하나의 포인트가 있어요.

> "데이터와 사양(仕様)은 UI 디자인의 재료다."

욕구만 알아서는 UI를 못 만들어요. 그걸 구현할 정보, 즉 데이터와 처리 방식(사양)이 같이 있어야 합니다.

![금융 관련 그래픽 사용자 인터페이스 화면](https://unsplash.com/photos/graphical-user-interface-0KMCxhGFKvc/download)
*출처: [Unsplash](https://unsplash.com/photos/graphical-user-interface-0KMCxhGFKvc)*

### 실무자의 시선 — UI = f(욕구, 정보)를 체감한 순간

이 공식을 가장 절실하게 체감한 건 AI 에이전트 CDJ 프로젝트였어요.

7단계 AI 파이프라인의 데이터 구조를 이해하지 않고는 UI를 설계할 수 없었습니다. 처음에 "키워드 분류 결과를 보여주는 대시보드"라고만 들었을 때는 막연했지만, 각 단계별 입출력 데이터 — 무관 키워드 제외 → 카테고리 분류 → CDJ 5단계 매핑 — 를 직접 학습한 후에야 CDJ 저니 차트라는 시각화가 나왔어요.

공식으로 풀면:

```
욕구(수작업 CDJ 보고서 제거) × 정보(7단계 파이프라인 데이터 구조) = UI(CDJ 버블 차트 + 수정 테이블)
```

어느 하나라도 빠지면 제대로 된 인터페이스가 나올 수 없었습니다.

### 커피 머신 앱에서 디자이너가 사양을 바꾼 순간

인상적인 사례 하나. 커피 머신 앱에서 팀은 "기기에 다가가면 자동 페어링되는 기능"을 원했어요. 사용자가 정말 원하는 건 "커피를 만드는 것"이고, 복잡한 연결 절차는 방해물이니까요.

엔지니어 답변은 "사양상 어려워요"였습니다. 그런데 마침 펌웨어 업데이트 기회가 생기자, 디자이너가 직접 "자동 페어링 사양 추가해 주세요"라고 요청해서 결국 실현됐어요.

> "좋은 UI를 위해 좋은 사양이 필요하면, 사양부터 만들면 됩니다."

### 현장에서 느낀 점 — 디자이너가 사양에 개입한다는 것

저희 회사에서도 이런 방향이 어느 정도 가능합니다. 디자인만 하는 게 아니라 기획을 함께 진행하거든요. 특히 데이터 분석 서비스이기 때문에 **디자이너가 데이터를 이해하는 것이 굉장히 중요**하게 다가왔어요.

쉽지는 않습니다. 데이터 파이프라인을 이해하고, SQL 쿼리 결과를 해석하고, AI 모델의 한계를 감안해서 UI를 설계하는 건 분명 어려운 일이에요. 하지만 바로 그 어려움이 경쟁력이기도 합니다. 데이터를 이해하는 디자이너가 만든 대시보드와, 와이어프레임만 받아서 그린 대시보드는 완성도가 다를 수밖에 없으니까요.

이토 씨가 "사양 자체에 관여하라"고 한 말이 디자인 영역의 확장처럼 들릴 수 있지만, 실은 **제대로 된 UI를 위한 필수 조건**이라는 걸 실무에서 계속 느끼고 있습니다.

---

## 팀 구조도 디자인의 일부

마지막으로 이토 씨는 팀 얘기를 꺼냈어요.

보통 IT 프로젝트는 "기획 → 디자인 → 개발" 순서로 흘러가잖아요. 근데 이렇게 되면 역할이 분리돼서, 추상과 구체 사이를 왔다갔다하기가 어렵습니다.

TeamLab은 늘 "전략부터 운영까지 다 같이 보게 해 주세요"라고 요청한다고 해요. 예를 들어 앱 로딩이 10초 걸리는 문제가 생기면, 엔지니어링으로 못 풀 때 디자인으로 풀어야 하니까요. 그 순간 전략 담당자도 같이 머리를 맞대야 한다는 거죠.

### 실무자의 시선 — 인하우스에서 '일관된 참여'가 주는 것

이 구조를 저도 인하우스에서 직접 경험했어요. 마이키워드에서는 고객사 인터뷰부터 QA까지 전 과정에 참여했고, AI 에이전트 CDJ에서는 AI 파이프라인 학습부터 시각화 설계, MVP 개발 협업 리드까지 했습니다.

인하우스의 장점은 이 **일관성**이에요. 제품의 맥락을 온전히 이해하고 있기 때문에, 전략적 판단이 가능합니다. "이 기능은 사용자가 원하는 게 아니라 우리가 만들고 싶은 거다"라는 판단을 디자이너가 할 수 있게 되는 거죠. 반면 에이전시는 다양한 도메인 경험을 빠르게 쌓을 수 있지만, 실제 비즈니스 임팩트를 끝까지 확인하기 어렵습니다.

커리어 관점에서는 **"문제를 깊이 판 경험"**이 포트폴리오에서 차별화됩니다. 처리 시간 99% 단축 같은 성과는 인하우스에서 끝까지 관여했기에 가능했어요.

---

## 마치며

이 발표에서 인상적이었던 건, 특별한 비법이 있는 게 아니라는 점이었어요.

"기대를 뛰어넘는다"는 건 사용자를 깜짝 놀라게 하는 트릭이 아니라, 그들이 진짜 원하는 걸 이해하고 구조적으로 풀어내는 거였습니다.

다음 프로젝트가 막막할 때, 이 질문을 한번 던져 보면 어떨까요?

**"이 UI를 쓰는 사람은 뭘 원할까? 그리고 그다음엔?"**
